# 中文化實作後的模擬器優化盤點

2026-09-05。這是程式碼審查與本次功能驗收形成的 backlog，**不是效能 profiler 報告**。以下工時皆粗估，沒有量測就不宣稱能快幾成。本輪先記錄，不把高風險重構和主線合併混在一起。

## P0：操作正確性與信任

1. **暫存語意一致（約 1–2 小時）**：目前原生 NES 為最近 16 次完整記憶體快照，而非永久 16 個存檔槽。反覆覆寫同一槽仍會讓其他舊快照被淘汰，前端槽位記錄可能到讀取失敗才知道過期。讓核心回傳可用 token／使用 slot-aware 替換，UI 顯示當次執行、有效／過期、儲存時間；所有入口共用訊息。證據：[核心](../nes-wasm/src/emulator.rs)、[前端](../src/main.ts)。不是每 16 幀過期。
2. **讀檔中文一致性（約 2–4 小時）**：硬體已完整恢復，但文字觀察證據重設，既有對話可能變回日文。將來源已驗證的圖層狀態與快照配對，恢復時重新核對 PPU 世代／字庫，不用截图猜字。加換 ROM／重設／重複讀檔回歸。
3. **可攜式存檔另立里程碑（先 2–4 小時設計）**：目前刻意拒絕舊不完整資料。需版本、ROM／核心識別、全部 mapper／APU／DMA 狀態、長度限制、原子驗證、升級策略與跨重啟測試；不能只把 in-memory token 下載成檔案。完整工時待核心範圍盤點。

## P1：先量測，再降低中文顯示成本

建立基準（約 1–2 小時）：同 ROM／輸入重播、相同縮放與裝置，中文關／開比較；記錄核心 step、overlay、menu matching 的 p50/p95、長任務、配置量、WASM memory 增長、音訊 underrun。至少桌機與一台實際手機，排除背景分頁 rAF 停滯與 HMR 干擾。60Hz 幀預算約 16.67ms，但應報各階段耗時，不只平均 FPS。

可驗證的候選（約 2–6 小時實作，按量測決定）：

- [圖層](../src/game-profiles/text-overlay.ts) 每次合成建立 framebuffer 副本、可能另建 sprite buffer／ImageData，並重建 Map／Set。可重用固定 buffer、文字寬度快取與預編譯 menu pattern，降低配置與重複工作。
- 原畫面與中文合成各自上傳 Canvas，可探索無遮罩／無中文時跳過額外合成；有中文時仍保持正確原生像素遮罩與 winning sprite 順序。
- **不能因字沒變就跳過所有驗證**：palette、CHR、世代、sprite 與滚動均能改變安全位置。dirty cache 的 key 必須包含實際來源證據。
- `measureText()` 重複 shaping 值得量測／快取，但不能稱它必然造成 DOM layout thrashing，也不是每幀處理全部 2,199 筆譯文。
- WASM 記憶體增長會使 view 失效；重新取得 buffer 是正確性保護，不應為少一次呼叫而快取已失效 view。buffer 共用只能在所有可能配置的呼叫之後建立。
- [卡帶](../nes-wasm/src/cartridge.rs) 的深複製包含 ROM vector，16 次完整快照增加記憶體。先量測 peak，再考慮不可變 ROM 共用／只複製可變狀態；不得共享 mutable mapper／RAM 而破壞快照。

驗收：同一輸入的硬體／原 framebuffer 與既有安全遮罩測試不退步，再比較 p95、配置量與音訊，不以「感覺順」過關。

## P1：版面與輸入體驗（約 2–4 小時首輪）

- 統一 MENU、鍵盤、觸控的暫停／存讀檔／返回行為與提示；危險動作（重載、離開將失去暫存）給清楚提醒。
- 加入短期可關閉的按鍵說明、手把對應、焦點／鍵盤導覽；遊戲方向選單的規則不要誤當作按鍵無效。
- 對手機橫直向、safe area、瀏覽器列收合、虛擬按鈕多點觸控、contain letterbox 建立固定驗收矩陣；保持方向盤與 A/B 同按、不捲頁、不讓選单遮住必要資訊。
- 維持既有視覺設計，先修狀態回饋、可讀性與觸控可達性，不因中文化順手全面改版。

## P2：架構與開發效率

- [main.ts](../src/main.ts) 已集中多核心生命週期、輸入、音訊、儲存、UI 與中文化。按 backend／save service／display pipeline 拆模組（首輪約 4–8 小時），先建立介面與回歸，不同時重寫所有核心。
- 將遊戲 adapter、catalog／storage key／editor route 参数化（約 2–4 小時，可併入 Zombie Hunter 樣本），禁止「通用層」硬寫另一款遊戲的 PC。
- 開發證據工具：固定輸入重播、snapshot hash、狀態診斷、各 writer 覆蓋報告，避免長時間人工重玩（首輪約 2–4 小時）。
- CI 分兩層：無 ROM 的公開單元測試／build，及本機持有 ROM 的 opt-in 整合測試。本輪不新增 ROM；版本化來源定義與可重建工具。現有 [Pages 工作流程](../.github/workflows/deploy.yml) 在 main push 後建置／部署，沒有獨立的上述測試關卡；push 成功不等於網站部署成功。儲存庫本來已追蹤 ROM，授權與公開發佈清理須另外盤點，不能宣稱現況為無 ROM 儲存庫。
- 翻譯版本三方合併與正式發佈驗證，避免舊本機草稿遮蔽新版縮句；固定字型若要打包先核對授權。

## 建議執行順序

先完成暫存提示／讀檔證據 → 建立效能基準 → Zombie Hunter 1–2 小時可行性樣本 → 按量測優化合成 → 再拆 main 與規劃可攜存檔。不要先更換 CPU／PPU 核心、降低音訊品質、減少來源驗證或大改 UI 來追求未量測的效能。
